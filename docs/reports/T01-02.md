## What was built

### Email and notifications (PRD-00 §17, TECH-02 §10)

- **`packages/email`**
  - `EmailSender` with four transports: Resend (HTTP API, with our notification ID as its idempotency key), SMTP (for Mailpit), a local file transport (`.outbox/emails`) and an in-memory transport for tests. `createEmailSender` picks one from `EMAIL_TRANSPORT`.
  - Resend 4xx errors other than 429 are permanent failures (no retry); 5xx and 429 are retried.
  - React Email templates: sign-in link, email code, secure (guest) link, new help request (to staff), help request received, help reply and test email. Colours and sizes come from the design tokens. Every template's data has a Zod schema.
  - `seal`/`unseal` (AES-256-GCM, key from `DATA_ENCRYPTION_KEY`).
- **Database:** table `notifications` (template, recipient, customer, record, link label, status QUEUED/SENT/DELIVERED/FAILED, attempts, provider message ID, safe last error, sealed data, resend-of).
- **`queueEmail()`** stores the notification and queues `email.send` in the business change's transaction. `email.send` retries 8 times (TECH-02 §8). Controllers never send email; a test checks the source code for this.
- **Worker `email.send` handler:**
  - Safe to run twice.
  - After a permanent failure, or once retries run out, the notification becomes FAILED.
  - Once an email that carried a link secret or code is sent, its sealed data is wiped.
- **Sign-in magic links** now go through `queueEmail` (template `sign_in_link`). The local file outbox is gone, and the "not in production without email" guard is lifted.
- **Admin notification log** at `/admin/notifications` (CUSTOMER_SUPPORT, Pen frame 102):
  - status and search filters, table and detail panel (to, attempts, provider ID, error, link)
  - "Resend email" creates a new record and keeps the old one, and is audited
  - emails that held a link or code can't be resent (422 `CARRIES_SECRET`): the person asks for a new one
  - empty, error and 403 states, plus a "queued again" notice
  - "Send test email" API (`POST /v1/admin/notifications/test`)
- **DNS checklist:** `docs/ops/EMAIL-DNS.md` (SPF, DKIM, DMARC; `p=quarantine` then `p=reject`).

### Customers, guest links and email codes (PRD-00 §5, §11; TECH-03 §2, §5, §6)

- **Customers:** table `customers`, one row per normalized email, with or without a user. `ensureCustomer()` finds or creates it. `linkCustomersToVerifiedEmail()` links rows with that exact verified email to an account; T09-01 calls it after verification.
- **Guest links** (table `guest_links`):
  - Stores the hash, purpose, target, customer, expiry, revoked time and who revoked it.
  - `createGuestLink()` returns the secret once (32 random bytes). The URL is `/l#<secret>`: the secret sits after `#`, so browsers never send it to any server or log.
  - Default lifetimes follow TECH-03 §5.
- **Redeeming a link** (`POST /v1/guest-links/redeem`, GUEST_LINK_VERIFY limit):
  - Sets an HttpOnly, SameSite=Lax `hp.guest` cookie for a guest session (table `guest_sessions`, token hash only, at most 30 days and never past the link's expiry).
  - Returns a clean path with `Referrer-Policy: no-referrer`.
  - An expired link returns 422 `LINK_EXPIRED`, a revoked one 422 `LINK_REVOKED`, an unknown one 404.
  - Revoking a link (`POST /v1/admin/guest-links/:id/revoke`, audited) ends every session made from it at once.
- **Web `/l` page:** takes the secret from the fragment, removes it from the address bar and history straight away, redeems it and moves to the clean URL. It has expired, turned-off and broken-link states.
- **`ActorContext`** gains a `guest` type (guest session, customer, target, when an email code was last verified). A signed-in session always wins over a guest cookie.
- **Email codes** (table `email_codes`):
  - `POST /v1/email-codes` sends a 6-digit code, stored as an HMAC. It lasts 10 minutes, and a new code replaces the old one.
  - `POST /v1/email-codes/verify`: a wrong code returns "That code isn't right. N tries left." After 5 tries the code locks; expired and used codes are refused.
  - `requireRecentEmailCode()` enforces the 24-hour window and returns 403 `RECENT_EMAIL_CODE_REQUIRED`, a new error code.

### Help requests (PRD-00 §18, PUB-FR-015, PROJ-FR-008)

- **Tables:** `help_requests` (reference `HR-YYYY-NNNN` from a sequence, status OPEN/ANSWERED/CLOSED, customer, user or guest session, message, context as JSONB) and `help_replies` (insert-only by trigger).
- **Context schema** (`helpContextSchema`): page, step, product, configuration, project, quote (with version), proof (with version), order, organization, location and files. IDs and short labels only; unknown fields are refused.
- **`POST /v1/help-requests`**:
  - Guests give an email; signed-in customers use their account's.
  - A person with no session gets a guest session for their own request.
  - Staff are emailed (`HELP_INBOX_EMAIL`) and the customer gets a confirmation.
- **`GET /v1/help-requests/:id`**: the policy `canViewHelpRequest` shows a request only to its account or guest session; anyone else gets 404.
- **Reusable `NeedHelp` component (web):** a dialog that attaches the page's context, with guest email and name, validation, sent and failure states. It is on the `/dev/slice` demo page.
- **Customer page `/help/:id`:** the question, status and HolyPearls' replies.
- **Admin help inbox** at `/admin/help` (CUSTOMER_SUPPORT, Pen frame 103):
  - status tabs with counts and the request list
  - record header, "Context attached automatically" panel and replies
  - reply by email (marks ANSWERED, idempotent, audited) and close (audited)
  - empty, error and 403 states, plus a "Reply sent" notice

## Tests

- **Email package (6):** every template renders to HTML and text; bad data is refused; secret-carrying templates are marked; sealing round-trips and refuses the wrong key; Resend 4xx is permanent and 5xx is retried; the memory sender can fail on purpose.
- **API (15 new, real database and an in-process worker):**
  - the test email is sent through `email.send`
  - a failing send retries (3 attempts at the test's retry limit) then shows FAILED in admin, and resend makes a new record and keeps the old one
  - secret emails are wiped after sending and can't be resent
  - the log is 404 for customers and 403 for staff without CUSTOMER_SUPPORT
  - no controller sends email directly (source check)
  - redeeming sets a scoped HttpOnly cookie and a clean URL, sends `no-referrer`, stores only the hash and never logs the secret
  - expired, revoked and unknown links are refused, and revoking ends existing sessions
  - codes: tries left, verification, one use only, lock after 5, expiry after 10 minutes, the 24-hour rule
  - linking an account's history works only on the exact verified email
  - a guest's help request carries its context, staff are emailed with the right subject, only that guest can see it (404 for others), staff reply (ANSWERED, email sent) and close it
  - signed-in customers' requests use the account's email
  - context with unexpected fields is refused, and so is a guest request with no email
  - the inbox is 404 for customers and 403 without CUSTOMER_SUPPORT
- **Browser (3 new, 375 and 1440 px, axe):**
  - A guest asks for help from the demo page, sees their own request, and a stranger gets 404.
  - Staff see the context in the inbox and reply; the guest then sees the reply.
  - The notification log loads.
  - A broken guest link explains itself and leaves no secret in the address bar.
- **Totals:** 73 API tests and 79 browser tests pass.
