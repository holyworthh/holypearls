S5b and S8b hold a row lock in the test, queue the two sides behind it in a fixed order (watching `pg_stat_activity`), then release. This makes the race happen every time instead of rarely. They still go through the real API.

## Fixes

- **R1 lock order.** `lockPaymentSource(tx, intentId)` locks the checkout (or installment). `applyResult` now locks source, then intent, then attempt, the same order as Pay. `resolveReview` calls it before the intent lock. Pay and a success can no longer deadlock.
- **R2 edit under a payment.** `startCheckoutPayment` bumps `checkouts.version` in `prepare`, so an edit that read the checkout before Pay committed fails its version check (409 `STALE_VERSION`). `CheckoutView` refetches the checkout after any Pay error, so the next edit uses the new version.
- **R3 final check dead-letters.** `settleUnanswered` (exported through `modules.ts`) settles the attempt as UNKNOWN with an UNCLEAR_RESULT review. The worker's `payment.check` dead-letter handler calls it for check 7 and the comment is corrected.

## Deviations from the plan

1. S1 accepts `STALE_VERSION` as well as `PAYMENT_IN_PROGRESS` for the 99 refused presses. After R2, a press that loaded the checkout before the first Pay committed sees the changed version. Both are 409.
2. S6 cannot demand exactly 60 rejections: checks that start after the first success skip Paystack. The test asserts `rejected = 60 - failures left`, and that success happens.
3. Added S5b and S8b because the random S5 and S8 did not fail on unfixed code, so they could not show R1 and R2 red. S5 and S8 stay as the 100-way versions.
4. Worker narrowing: `"attemptId" in payload` is needed for the type; `CHECK_SCHEDULE_SECONDS` is exported from `modules.ts`.
5. No 40P01 mapping, as planned.
