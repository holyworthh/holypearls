# T14-01b: Search quality and analytics

Status: IN REVIEW.

## Plan (approved in advance by the owner)

Plan: `holypearls-plans/T14-01b.md`. Key decisions:

- **Full catalogue only in the quality test.** `launchCatalogueSeedStep` loads all 304 Stage 1.4 rows. It is not in `buildSeedSteps`, so dev, staging and e2e keep the small catalogue.
- **"First result"** means the first entry of the expected type's group (Products, Projects or Guides), because results are grouped by type (PUB-FR-006).
- **Result order:** an exact title or exact phrase first, then `ts_rank_cd` (default weights), then popularity, then name. Product phrases are stored one per line so an exact phrase can be told from a word inside one. Tuning is by data (phrases), never per query.
- **Phrase coverage:** one SQL query (a lateral lookup per phrase) checks each indexed phrase puts its own page first.
- **Analytics:** one lean `site_events` table (kind and `fromGuide` only, no text), `POST /v1/analytics/events` (PUBLIC_READ rate limit, CONFIGURE refused), a click listener on every page, and a fire-and-forget CONFIGURE event when a design is first saved (TECH-00 §9). Retention: 90 days, in the existing cleanup.
- **Report:** `GET /v1/admin/search/report` now returns result clicks, a zero-result list (50, with last-searched date), entries by kind, and phrase coverage. It is shown at `/content/search-report`; the report panel left the phrases page.

## Deviations from the plan

- **Missing Origin is not refused by itself.** The plan said a POST without Origin is refused "as the existing CSRF rule does". The rule (`origin-check.ts`) refuses a foreign Origin, and a missing Origin only when a session cookie is sent. The test checks exactly that.
- **`phraseCoverage` SQL** casts both `case` branches to `search_doc_type[]` (the plan cast once after the `case`), to avoid a text[] versus enum[] mix.
- **New subcategory slug:** a sheet subcategory gets its plain slug, and the `-<parent slug>` form only when that slug already belongs to another parent ("Custom" sits under three).
- **Test timeouts** are raised (300 s, 120 s, polling 30 s) because the test database is remote.
- **`pnpm db:migrate` and `pnpm seed`** were not run against the shared dev database (they would change it for other tickets). The migration runs from empty in every API test database, and `db:check` passes. Browser tests ran on a throwaway database.
