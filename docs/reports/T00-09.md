# T00-09 and T00-10 — Separate admin app, and the API serves admin only to it

Status: IN REVIEW (pending CI and merge). Covers T00-09 and T00-10 in one pull request, so the customer site never ships without the API guard. T00-11 (hosting) follows.

Branch `feature/t00-09-admin-app`. Owner decision of 1 October 2026: the admin must not live on the customer domain (ADR-017).

## What was built

### T00-09: the admin app
- **`apps/admin`** (Next.js, port 3002) holds every former `/admin` page, the admin shell, staff sign-in and authenticator set-up.
  - Paths lose their `/admin` prefix (`/products`, `/help`, `/sign-in`); the whole subdomain is admin.
  - Links to public pages ("view live page", hub preview, search-phrase targets) use the customer site's address (`SITE_URL`, `src/lib/site.ts`).
- **Locked down by default:**
  - Every response sends `X-Robots-Tag: noindex`, `Cache-Control: private, no-store` and `Referrer-Policy: no-referrer`.
  - `robots.txt` disallows everything.
  - A stricter CSP than the customer site: no third-party scripts, and no frames at all.
- **Non-staff:** a customer who signs in on the admin is signed straight out and told the details didn't work. The API refuses them anyway (below).
- **`packages/web-kit`** (new, TypeScript source like `packages/ui`) is used by both apps:
  - the API client, server-side API calls (`createServerApi` per front end), the proxy headers (`visitor.ts`), money formatting, catalogue labels, file upload, and the sign-in styles.
  - The customer app keeps thin re-exports, so its own code barely changed.
- **Customer app:**
  - `/admin` and staff sign-in are gone.
  - Its proxy returns 404 for `/api/v1/admin/*` and the authenticator steps (`/api/v1/auth/two-factor/*`).
  - TipTap and `qrcode` moved to the admin.
  - The customer sign-in no longer hands staff on to an admin page.
- **CI guard:** `pnpm --filter @holypearls/web check:no-admin` fails the build if the customer build holds an admin route or code that calls admin API routes or the authenticator steps.

### T00-10: the API knows which front end is calling
- **`apps/api/src/identity/front-ends.ts`:**
  - Each proxy sends `x-hp-surface` and its own secret. The secret decides: the header alone proves nothing.
  - With `ADMIN_PROXY_SECRET` unset (locally) the admin is known by its origin.
  - With `ADMIN_ORIGIN` unset, the API serves one front end as before. Only local runs and older tests do that: production refuses to start without it.
- **Boundary:** with two front ends,
  - `/v1/admin/*` and the authenticator steps answer 404 anywhere but the admin, and `StaffGuard` refuses them too;
  - email sign-in links answer 404 on the admin.
- **Origins:** the origin check (TECH-03 §13) compares each request with its own front end's origin.
- **Sign-in:** staff sign in only on the admin and customers only on the customer site. The refusal is the same 401 as a wrong password (same code, reason and no cookie), so neither site reveals which emails are staff.
- **Visitor address:** either front end's secret vouches for it (review P1-08).
- Better Auth trusts both origins, and the help-inbox email links staff to the admin.
- **Config (`packages/config`):**
  - **api:** `ADMIN_ORIGIN` and `ADMIN_PROXY_SECRET`. In production both are required, the admin must be on its own domain (not `localhost` or `.test`), and its secret must differ from `WEB_PROXY_SECRET`.
  - **admin app:** `loadAdminEnv` reads `API_URL`, `SITE_URL` and `ADMIN_PROXY_SECRET`. The secret is required in production, and the site address can't be `localhost` there.

## Tests

- **`apps/api/src/identity/front-ends.test.ts`** (TECH-03 §17):
  - admin routes are served through the admin proxy and hidden from the customer site, from no proxy, and from a forged surface header;
  - the authenticator steps are hidden from the customer site;
  - each front end's origin is enforced;
  - staff are refused at the customer sign-in exactly like a wrong password;
  - customers are refused at the admin sign-in;
  - email links are customer-only;
  - catalogue and cart are unchanged.
- **Config:** production needs the admin on its own domain with its own secret, and the admin app's production rules hold.
- **E2E:** the admin app runs beside the customer site (ports 3200 and 3100) and the admin steps go to it. The suite stays in `apps/web` because it tests whole journeys across both sites (staff publish, then the public page changes). A new check covers the customer site: `/admin` is 404, `/api/v1/admin/me` is 404 and the authenticator steps are 404. Another checks that the admin's robots.txt disallows everything.
- **Not changed:** every existing API test runs with one front end and passes unchanged.

## Deviations and notes

- **E2E location:** the plan put the admin e2e tests in the admin app. They stay in `apps/web` and drive both sites, because most admin tests check the public result of a staff action.
- **Locally both apps share `localhost` cookies** (cookies ignore the port). Deployed, they are on different domains with host-only cookies, so a staff session never reaches the customer domain (TECH-03 §4).
- **The design-system demo page** on the customer site still shows the admin shell component, with sample data, because it demonstrates `packages/ui`. It holds no admin pages or API calls.
- **Staging gap until T00-11:** once this merges, staging's customer site no longer serves `/admin`, and its API (still with one front end) has no admin app until T00-11 deploys it. T00-11 follows straight after.
