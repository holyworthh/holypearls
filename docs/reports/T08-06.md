## What it does
- **Book courier.** A shipment of an order whose delivery a courier priced at checkout shows a "Book courier" button on its card in Shipments while it is PREPARING.
  - The rate is asked for again, for the items in this shipment only, because the checkout's rate has gone stale (its pickup date has passed). A split order books each shipment with its own parcel.
  - The courier service the checkout priced is booked when it's still offered. If not, the courier rule (cheapest or fastest) picks another, and the history says so.
  - Shipbubble's order ID, the service, its tracking page and the cost before VAT are kept on the shipment. The carrier and any tracking code fill in, and the shipment moves PREPARING → LABEL_CREATED with a history entry and an audit entry.
  - **Price changes (owner, 2026-10-07):** when the courier now costs more than delivery was priced at, the booking goes ahead. The difference is HolyPearls' cost, written in the history note and in the audit entry (cost and priced amount). The customer is never charged again.
  - Two clicks can't book twice: the shipment is locked while Shipbubble answers, the second request gets "changed by someone else", and the request is idempotent.
  - If Shipbubble fails or courier prices are off, nothing changes and staff see why.
- **Webhooks.** `POST /v1/webhooks/shipbubble` checks Shipbubble's `x-ship-signature` (HMAC-SHA512 of the raw body, keyed with the API key, as [Shipbubble documents](https://docs.shipbubble.com/api-reference/webhooks)). Each event is kept once, by a hash of its body, because Shipbubble resends failed events unchanged and gives them no ID.
  - Statuses: `pending` and `confirmed` → LABEL_CREATED; `picked_up` and `in_transit` → IN_TRANSIT; `completed` → DELIVERED; `cancelled` (or `shipment.cancelled`) → EXCEPTION.
  - **Only legal TECH-01 moves.** A webhook takes the shortest legal run of statuses and records each step, never passing through ATTEMPTED_DELIVERY, EXCEPTION or RETURNED. Shipbubble has no "out for delivery", so `completed` after `in_transit` records IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED: no status is skipped (OPS-FR-073).
  - **A move that isn't allowed** (for example "cancelled" after DELIVERED) changes nothing. It's written on the shipment's history as a note for staff (same status before and after) and in the audit log. Customers never see these notes.
  - The dispatch and delivered emails go out exactly as for moves made by hand (the same code path).
  - A tracking code or tracking page sent later (`shipment.waybill.updated`) is filled in.
  - Events for unknown orders and wallet events are accepted, kept and ignored.

## Permission rules added
- Booking needs FULFILMENT_MANAGE: staff without it get 403, customers 404, signed-out visitors 401/404. Tested, with no booking made.
- The webhook takes no cookie; a missing or wrong signature is 403 and changes nothing. Tested.
- Customers' shipment views never include Shipbubble's order ID, the cost or staff-only notes. Tested.

## Differences from the plan, and why
1. **No label PDF is stored.** Shipbubble's create-shipment response has no label or waybill link, only a tracking page, so the tracking page is kept and shown. Couriers print their own waybill at pickup.
2. **No email at booking.** As before, the customer is emailed when the shipment leaves (IN_TRANSIT) and when it arrives. Booking makes a label, which isn't news to the customer.
3. **Webhooks are applied straight away, not in a job.** The work is a few rows and Shipbubble wants an answer within 15 seconds. A failure returns an error, so Shipbubble retries (every 5 minutes, 5 times).

## Questions and notes
1. **Booking is a paid call to Shipbubble that can't be undone from here.** If the database write after a successful booking ever failed, the booking would exist at Shipbubble without a record here. It is one short transaction, so this is unlikely, but staff should cancel a stray booking in Shipbubble's dashboard if it ever happens.
2. **The shipment is locked while Shipbubble answers** (up to three calls, each with an 8-second limit), so a staff member opening the same shipment waits briefly.
3. **Owner to do:** in Shipbubble's dashboard, set the webhook URL to `https://<api domain>/v1/webhooks/shipbubble` for the sandbox and the live account.
