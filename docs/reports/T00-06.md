# T00-06 — Sign-in, staff accounts, MFA and admin shell

Status: DONE (merged after CI passed). This ticket includes the former T00-07.

Commits / PR: branch `feature/t00-06-sign-in-staff-mfa`; pull request linked in `docs/tracker/TICKETS.csv`.

## What was built

**Identity (`packages/auth`)**

- `IdentityAdapter` has `handle`, `getSession`, `listSessions`, `revokeAllSessions` and `revokeSession`. Nothing outside `packages/auth` imports Better Auth (TECH-03 §3, ADR-005).
- `createBetterAuthIdentity()` runs Better Auth 1.7.6 inside the API. It uses the Drizzle adapter on our own Postgres and UUIDv7 IDs. Neon is only the database (approved; Neon Auth is not used).
- Sign-in methods:
  - Email and password. The minimum length is 12, matching the Pen hint.
  - Magic link: 10 minutes, one use.
  - Authenticator app (TOTP), via Better Auth's `twoFactor` plugin. Secrets and backup codes are stored encrypted.
- Sign-out, and "sign out everywhere".
- Sign-up is off until the customer sign-up screens in T09-01.
- Sessions follow TECH-03 §4:
  - Cookies are named `hp.*` and are HttpOnly, SameSite=Lax and host-only.
  - They are Secure whenever `BETTER_AUTH_URL` is HTTPS.
  - Customers get 30 days, refreshed daily.
  - Staff sessions end 12 hours after sign-in. The session is created with a 12-hour expiry, and `getSession` also caps it at `createdAt + 12h` even if it was refreshed.
  - Changing a password ends other sessions (`revokeOtherSessions` is forced). Resetting a password ends all sessions.
  - There is no cookie cache, so a revoked session stops working on the next request.
- `mfaVerifiedAt` on the session is set after every successful authenticator check. It drives both the MFA gate and the 15-minute recency check.
- Sign-in rate limits: 5 per minute for email sign-in, 3 per minute for magic links, 5 per minute for authenticator codes. `AUTH_RATE_LIMIT=off` exists for browser tests only.
- `MemoryOutbox` (tests) and `FileOutbox` (development: `.outbox/auth-emails.jsonl`, git-ignored). The API refuses to start with `NODE_ENV=production` until T01-02 provides the email sender.
- Better Auth's own warnings and errors go to our redacted JSON logger, message only.
- Test helpers:
  - `TEST_PEOPLE`: two STAFF_ADMIN users with MFA, one CATALOGUE_MANAGE staff member without MFA, and two customers, all TEST DATA on `.test` addresses.
  - `insertTestPerson()` inserts one of them into a database.
  - `signInAs(key, { authUrl, origin })` signs in through the real routes, including the authenticator step.
  - `totpCode(secret)` returns the current authenticator code.

**Database (migration `0001_identity`)**

- Better Auth's tables: `users`, `sessions` (with `mfa_verified_at`), `accounts`, `verifications`, `two_factors`.
- `staff_profiles` (with `staff_status` ACTIVE or DEACTIVATED).
- `staff_permission_grants`, using a `staff_permission` enum of the 16 TECH-03 §8 permissions. The pair (staff member, permission) is unique, and each grant records `granted_by_staff_id`.
- The permission list lives in `packages/contracts` (`STAFF_PERMISSIONS`) and is shared by the database, API and web.

**API**

- The API builds a minimal `ActorContext` (anonymous, or user plus active staff profile and permissions) once per request, on first use. Organization memberships, customers and guests arrive in later tickets.
- `StaffGuard(permission?)` does all staff checks in one place:
  - Not staff, or deactivated: 404.
  - Staff with no authenticator check in this session: 403 `MFA_REQUIRED`.
  - Staff without the named permission: 403 `FORBIDDEN`.
- `requireRecentMfa()` returns 403 `RECENT_MFA_REQUIRED` when the last check is older than 15 minutes.
- Origin check (TECH-03 §13): a state-changing request from another origin is refused. So is one with no Origin that carries a session cookie. Better Auth's own check stays on.
- `/v1/auth/*` is bridged to the adapter. Its errors are rewritten into the one error shape, with the library's code in `context.reason`. Session tokens are removed from JSON bodies, so they only travel in HttpOnly cookies.
- Endpoints, all in OpenAPI:
  - `GET /v1/me`
  - `GET /v1/me/sessions` (device described as "Chrome on Windows", never the raw user agent)
  - `POST /v1/me/sessions/revoke-all`
  - `GET /v1/admin/me`
- New error codes: `MFA_REQUIRED` and `RECENT_MFA_REQUIRED`.

**Web**

- `/sign-in` (Pen 87): Password and magic-link tabs, an error summary with field errors, a failure banner, rate limited, link sent (with resend and go back), link expired or already used, and "Signing in…".
- `/account/security` (Pen 90): a server-rendered signed-in page with the account nav, the password card, the sessions list with "This device", a confirm dialog for "sign out everywhere", and the success, error-with-retry and loading states.
- `/admin/sign-in` (Pen 93):

  - Top bar with the breadcrumb, "MFA verified · N min ago" and the staff name and role line.
  - At 375 px, a menu button opens the nav.
  - Operations home placeholder.
  - `/admin/[section]` shows the 403 permission-denied card inside the shell when a permission is missing. Otherwise it says which ticket builds that section.
  - Non-staff get the 404 page with HTTP 404. The page title stays neutral, because metadata waits for the access check.
- `proxy.ts` gives every page request an `x-request-id`, which `serverApi()` forwards to the API with the visitor's cookies. This closes the T00-03 question about request IDs from the web server.

## Permission rules added

- `StaffGuard` for staff admin routes, and `requireRecentMfa` for high-risk staff actions.
- The TECH-03 §17 negative tests that apply now:
  - Non-staff and signed-out people get 404 on admin.
  - Staff without MFA are blocked.
  - Staff without a permission get 403.
  - A deactivated staff member loses access immediately.
  - A request from another origin is refused.

## Screens checked

Rendered at 375 and 1440 px and compared with Pen 87, 90, 93 and 94. Differences:

1. The public header on sign-in and security is the T00-05 `PublicShell` (logo only), not Pen's full header with nav, search and "Start a Project". The full header arrives in T02-03 (navigation).
2. Pen's sign-in page has no footer; `PublicShell` shows one.
3. The account security "Password" card has no "Change password" button. The change-password screen is T09-01, and a dead button would mislead.
4. Session rows show the device and last activity, but not a city ("Lagos · active now"). IP-to-city lookup is not in scope.
5. The admin top bar leaves out the search field (search is T10-03 and T13-03), and nav items have no counts yet.
6. Sidebar and nav icons are neutral placeholders; Pen uses generic 18 px icons.
7. Staff enrolment asks for the password again when someone returns later through "MFA required". Better Auth requires the password to add an authenticator. Pen's enrolment frame has no password field, because it assumes enrolment straight after sign-in, which is how the first-time flow works here.
8. Field labels use the design-system label weight (500); Pen frames show 600.
9. The step-up dialog (`HP/Admin/StepUpMFA`) is not a component yet. The API side (`RECENT_MFA_REQUIRED`) is done and tested; the dialog comes with the first high-risk action (T13-05, refunds).

## Questions / conflicts found

- ADR-005 is now Accepted (edited in `docs/plan/ADR-REGISTER.md`, as the ticket asked).
- **Your `.env` changed.** `BETTER_AUTH_URL` now holds the web origin (`http://localhost:3000`), not the Neon Auth URL, and there's a new `BETTER_AUTH_SECRET`. That is the approved in-API setup.
- **Every environment needs this.** The Next build writes `API_URL` into the `/api` forwarding at build time, so each environment's web build must be made with its own `API_URL`. Note this for T00-04 (staging).
- **MFA reset needs its own UI.** RESOLVED 2026-09-28 (owner: add it). It's already in T13-05's Build scope (staff administration: "MFA reset"). There, a STAFF_ADMIN resets another staff member's authenticator, with recent MFA and an audit entry. The policy `canResetStaffMfa` already exists (T01-01).
- **Other sign-in routes Better Auth provides.** RESOLVED 2026-09-28 (owner: best practice). The API now forwards only an allowlist of the routes HolyPearls uses; everything else (email change, account deletion, backup codes, removing the authenticator, account linking, user updates) returns 404. An allowlist, rather than `disabledPaths`, means a library upgrade can't quietly add a route. Tested. T09-01 adds routes to the list as customer screens need them.
