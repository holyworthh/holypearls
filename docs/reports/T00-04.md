## What was built

**`packages/jobs`** (job helpers, TECH-00 platform module)
- The `Jobs` class wraps pg-boss 12.35.0. It connects through `DATABASE_DIRECT_URL` (Neon's unpooled URL) and falls back to `DATABASE_URL` locally (TECH-07 §1).
- Default settings for every queue (TECH-02 §8): 5 retries, backoff starting at 30 seconds and doubling, a 5-minute timeout, and a dead-letter queue `<queue>.dead`. The `QUEUES` registry holds each queue's payload schema, with only the settings that differ from the defaults.
- Every payload is `{ v: 1, requestId, …resource IDs }` and checked strictly, so unknown fields such as email addresses are refused. Workers check payloads again before running.
- `send(queue, payload, { tx })` queues the job inside the business change's Drizzle transaction, so a rolled-back change leaves no job.
- `work()` and `workDeadLetters()`.
- Graceful `stop()`: running jobs get 30 seconds; unfinished ones retry later.
- Roles: the worker runs maintenance and scheduling; the API only sends.

**Worker (`apps/worker`)**
- Runs `demo.slice` jobs through the same service the API uses (`@holypearls/api/modules`, TECH-00 §5).
- Marks dead-lettered demo requests FAILED and reports them to monitoring.
- Logs "worker started" with its queues, one JSON line per job, and a "worker status" line every minute with queue sizes and the last successful job per queue (TECH-07 §8).
- Stops gracefully on SIGINT and SIGTERM.
- Uses a bounded pool of 5 connections.

**End-to-end slice (TECH-00 §14)**
- Table `demo_slice_requests` (migration `0002_demo_slice`).
- `POST /v1/demo/slice` saves the message and queues `demo.slice` in one transaction. `GET /v1/demo/slice/:id` returns it.
- The worker job puts the message in capitals and sets DONE. It is safe to run twice. A message containing "fail" throws, to show the retries and then FAILED from the dead-letter queue.
- The web page `/dev/slice` has the form, polls every second and shows the result.
- The API, the web page and the demo all switch on only with `HP_DEMO_SLICE=on`. The API refuses to start with the demo on when `HP_ENV=production`.

**Staging preparation (not deployed)**
- Root `Dockerfile`: one image for the API and the worker, plus the release command `node packages/db/dist/migrate-cli.js`. There's also a `.dockerignore`.
- `HP_ENV` (local, preview, staging or production) replaces `NODE_ENV` in the "never in production" guards. Staging can run `NODE_ENV=production` for speed without tripping them.
- Sentry (`@sentry/node` 11.0.0) for the API and the worker. It is off unless `SENTRY_DSN` is set. Events carry the request ID, route or queue as tags. Cookies, headers, request bodies and user details are removed before sending.
- `POST /v1/admin/monitoring/test-error` is for staff with SECURITY_ADMIN only (403 for other staff, 404 for everyone else). It is the "Sentry receives a test error" check.
- `docs/ops/STAGING.md`: services, commands, every environment variable, deploy order, the checks for "Done when", and the decisions needed.

## Tests (11 new)

- **Jobs (5, real database):**
  - The defaults match TECH-02 §8.
  - Bad payloads are refused, including extra fields.
  - A job queued in a rolled-back transaction doesn't exist, and one in a committed transaction does.
  - A failing job runs 3 times (with a test retry limit of 2), ends `failed` and reaches the dead-letter handler.
  - A job queued while no worker runs is picked up by a new worker. That shows a restart is safe.
- **Slice (4, API plus a real in-process worker):**
  - The request goes API → database → job → DONE with the result.
  - "fail" leads to retries, then FAILED.
  - Input is validated (400 with field errors), and an unknown ID returns 404.
  - Running the job twice changes nothing.
- **Monitoring route (1):** returns 500 for SECURITY_ADMIN, 403 for other staff and 404 when signed out.
- **Manual check:** in the local browser, API, worker and web were run against Neon. "hello from the browser" became DONE with "HELLO FROM THE BROWSER".
