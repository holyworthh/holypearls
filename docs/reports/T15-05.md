## Plan (approved in advance by the owner)

**Sources:** TECH-07 §5, §6, §12, §14; TECH-06 §10, §14; TECH-03 §4–5, §9, §17; Pen frame 123 (`S1fH7`, switches `JqxuW`, states `bCk9j`).

**Key decisions:**
- **Switches:** one single-row table `incident_switches` (migration `0059_incident_switches`) holds read-only mode and the upload pause as "on since" times. Payments pause stays in `payment_settings.online_payments`: it is the same switch as Payment settings.
- **Read-only mode** is one middleware after `originCheck`. Reads, the admin surface, `/v1/admin/`, `/v1/webhooks/`, order-link redeem and sign-in or sign-out pass. Everything else answers 422 `RULE_FAILED` with reason `READ_ONLY` and the maintenance message. Sign-up is blocked.
- **Every switch change** needs SECURITY_ADMIN, a recent authenticator check (`requireRecentMfa`) and an audit entry.
- **Alerts:** Sentry is the channel (tagged, fingerprinted events, one per signal and key an hour per process). Without `SENTRY_DSN` they are log lines. A1 and A2 are computed in the API process; A3 in the worker's dead-letter handlers; A4 to A9 by a new `ops.monitor` job every 5 minutes.
- **Secret rotation needs no code:** `BETTER_AUTH_SECRETS=2:<new>` with `BETTER_AUTH_SECRET=<old>` kept as the decrypt-only fallback. A test proves it.
- **R2 backup:** a daily copy of private files to `S3_BACKUP_BUCKET` (`storage.backup` job), not registered without the variable.
- **Release step:** no new code. The free tier already runs migrations at container start (CI checks it). The paid layout is in `docs/ops/LAUNCH-CHECKLIST.md`.
- **Restore rehearsal:** `deploy/restore-rehearsal.sh` restores the staging branch to an earlier moment of its own history. Production data never goes into staging.

## Questions / conflicts found

- **Q1 Sentry:** deferred at launch (2026-10-05) but the staging DSN was set (2026-09-28). Default used: Sentry is the alert channel; without a DSN, logs only.
- **Q2 Restore into staging** vs "staging never touches production data" (TECH-07 §2). Default: rehearse by restoring the staging branch to an earlier point.
- **Q3 R2 versioning (checked with Cloudflare's docs):** the S3 API page lists `PutBucketVersioning` as unimplemented. R2 does have **bucket lock rules** (dashboard: R2 → bucket → Settings → Bucket lock rules → Add rule; age-based, until a date, or indefinite; prefix optional; wrangler `r2 bucket lock add`). So the daily copy plus a retention lock rule on the backup bucket is the right design.
- **Q4 Business hours:** Monday to Saturday, 08:00 to 18:00 Lagos (default used).
- **Q5 Minimum sample:** 20 requests (default used).
- **Q6 Read-only** allows sign-in and sign-out, order-link redeem, webhooks and admin; it blocks sign-up. Confirm.
- **Q7 Deploys:** merging to `main` still deploys automatically; TECH-07 §15 says tagged commits. Suggestion only.
- **Q8 Neon history window** vs the 7-day requirement: the owner checks the plan.
- **Q9 Staging shares development's `BETTER_AUTH_SECRET`**, and beta testers' details would sit next to TEST DATA. Is that acceptable for a family beta?

## Risks

- On the free tier the monitor job and the request statistics only run while the container is awake. A sleeping site raises no alerts, and has no traffic to alert on.
- Request statistics are per instance (`ponytail:` comment); move to Sentry performance metrics with more than one instance.
- "Revoke sessions → Everyone" also signs out the person who presses it; the dialog says so.
- Backup copies are buffered in memory one file at a time (up to 100 MB) on a 512 MB container. Switch to server-side CopyObject if memory alerts appear.
