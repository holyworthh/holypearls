## What was built

- **Branch:** `feature/t09-01b-email-change`. **PR:** https://github.com/holyworthh/holypearls/pull/110.
- **Migration `0053_pending_email.sql`:** `users.pending_email` and `users.pending_email_at`, holding the new email while its check link is open.
- **Auth (`packages/auth`):**
  - **The sign-in library's own email change is turned on** (`user.changeEmail`, Better Auth 1.7). It sends a check link to the new address, and the account keeps its email until the link is opened.
  - **The new email's check** goes out as a new email kind, `CHANGE_EMAIL`. Better Auth sends it through the same hook as the sign-up check, so the kind is told apart by comparing with the stored email.
  - **After `/change-email`:** the pending email is recorded whatever the library did. When the address already has an account, the library replies the same and sends nothing; the pending state is the same too, so the profile never reveals whether an address is taken.
  - **After `/verify-email`:** when the account's email now equals its pending email, every other session ends, the pending email clears, and `onEmailChanged` runs. The device that opened the link stays signed in, because the library signs it in.
- **Email:** a new `change_email` template ("Confirm your new HolyPearls email"). It carries a secret, so it is sealed and wiped after sending like the other auth emails.
- **API:**
  - **Auth routes:** `/change-email` is allowed, under the AUTH rate limit and customer-only: the admin returns 404.
  - **Audit:** `security.email_changed` is recorded when the change completes. Linking guest records with the new email runs as for any verified email (TECH-03 §6).
  - **`GET /v1/me`** and the profile gain `pendingEmail`. It is empty once the 24-hour link has expired.
  - **`GET /v1/me/history/{list}`:** orders, quotes, projects, drafts or receipts, in full, newest first, up to 200. It reuses each module's own account function with a larger limit. An unknown list is 404. Documented in OpenAPI.
- **Customer site:**
  - **Profile (frame 91):**
    - The Email field can be edited, with the frame's hint ("Changing your email needs verification and signs you out on other devices").
    - Saving a new address sends the check and shows "Verify your new email · We sent a link to … Your email stays … until you verify", with "Resend link". The field goes back to the current email.
    - After the link is opened, the profile says "Email changed" and that other devices were signed out.
  - **List pages `/account/orders`, `/quotes`, `/projects`, `/drafts` and `/receipts`:** the account navigation now links to them instead of sections of the overview.
  - **`components/account/HistoryRows.tsx`:** the overview's row renderers moved here so the overview and the lists share them; the overview looks the same.

## Permission rules added

- **Changing the email:** signed in, on the customer site only (the admin returns 404). The AUTH rate limit applies. A signed-out request is 401.
- **History lists:** the signed-in person's own records only, exactly as the overview. A signed-out request is 401.

## Differences from the design or PRD, and why

1. **No email to the old address about the change.** Neither TECH-03 nor frame 91 asks for one. Better Auth can ask the old address to approve first (`sendChangeEmailConfirmation`), which would be a stronger check. **Suggested** if account takeover becomes a concern.
2. **Cancelling a pending change:** not in frame 91. A pending change lapses with its 24-hour link, or a different address can be entered.
3. **Lists show up to 200** of each, newest first, with no paging yet. Paging can be added when an account gets near that.
4. **An unknown list (`/account/payments`) shows the not-found page with status 200, not 404.** The account area's loading state starts the response before the page decides. These pages are private and never indexed, so it only affects the status code. A real 404 would need the lists moved out of the loading boundary.
5. **The overview keeps its sections** with no "See all" links; the account navigation leads to the lists, as in frame 91.
