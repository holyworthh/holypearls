# T01-01 — Audit log, permission framework, rate limits and idempotency

Status: DONE (merged after CI passed). This ticket includes the former T01-03.

Commits / PR: branch `feature/t01-01-audit-permissions-limits`; pull request linked in `docs/tracker/TICKETS.csv`.

## What was built

**Audit log (OPS-FR-120, TECH-03 §15)**
- Table `audit_log` (migration `0003_platform`), with:
  - actor type (STAFF, USER, GUEST, SYSTEM) and the actor's name at the time
  - action (a machine name) and summary (a sentence)
  - record type, ID and label
  - before and after (JSONB)
  - the permission used
  - when MFA was last checked
  - request ID
- Insert-only for **every** database user. Migration `0004_audit_insert_only` adds triggers that refuse UPDATE, DELETE and TRUNCATE. With a single database user today, a trigger is the only guard that also binds the application's user. A separate read/insert-only role can be added with production (T15-05).
- `recordAudit(dbOrTx, actor, entry)` writes inside the business change's transaction.
- **Wired now:**
  - staff permission granted and removed
  - MFA reset by another STAFF_ADMIN
  - 5 failed sign-ins in 15 minutes (one alert per account per window)
  - authenticator set up or removed
  - password changed
  - signed out everywhere
  - signed out one device
- **Staff administration API** (the screens are T13-05):
  - `GET /v1/admin/staff/:id/access`
  - `POST /v1/admin/staff/:id/permissions` (idempotent)
  - `DELETE /v1/admin/staff/:id/permissions/:permission`
  - `POST /v1/admin/staff/:id/mfa-reset`: removes the authenticator, ends every session and forces re-enrolment
  - All need STAFF_ADMIN, an authenticator check in the last 15 minutes (TECH-03 §9) and the ADMIN_WRITE limit. The policy keeps at least two STAFF_ADMINs and refuses resetting your own MFA.
- **Audit viewer** at `/admin/audit` (AUDIT_VIEW):
  - search, action and date filters
  - table (stacked rows at 375 px) and an entry detail panel with action, permission, before, after, actor, MFA and request ID
  - cursor paging, 25 per page (maximum 100)
  - empty, error-with-request-ID and 403 states
  - API: `GET /v1/admin/audit`, `GET /v1/admin/audit/:id`

**Permission framework (TECH-03 §12)**
- `ActorContext` now carries the request time, so time checks such as MFA recency use one clock that tests can control.
- **Policy pattern:** `Decision` = allow, deny (403) or hide (404). `enforce()` turns a decision into the right error, and `findOrHide()` treats missing and not-yours the same (404). Controllers call policies; they never write permission `if`s.
- **Identity policies:** `canRevokeSession`, `canManageStaffAccess`, `canResetStaffMfa`, `canRevokePermission`.
- **Scoped query:** `findSessionForActor()` only ever loads a session together with its owner.
- **Example route:** `DELETE /v1/me/sessions/:sessionId` ends one of your own sessions; another person's session returns 404.
- **Test helpers:** `signInActors`, `as(harness, cookie)`, `expectHidden` (404), `expectForbidden` (403, with a reason), and `expectOutcomes` (the same request as several actors).

**Rate limits (TECH-02 §14, ADR-013)**
- Table `rate_limit_buckets`: fixed windows, one upsert per rule. Keys are SHA-256 hashes, so no raw IPs or emails are stored.
- The TECH-02 classes: PUBLIC_READ, SEARCH, AUTH (10 per minute per IP and 5 per 15 minutes per account), GUEST_LINK_VERIFY, UPLOAD_INTENT, COMMERCIAL_WRITE and ADMIN_WRITE.
- `@RateLimit(class)` on a route, enforced by a global guard. 429 `RATE_LIMITED` carries a `Retry-After` header and `retryAfterSeconds`.
- The sign-in routes (sign-in, magic link, authenticator code, sign-up, password reset) use the AUTH class in the API. **Better Auth's in-memory limiter is now off**: it counted each API instance separately.

**Idempotency (TECH-02 §4)**
- Table `idempotency_keys` (actor, key, request fingerprint, stored result, 24-hour expiry).
- `@Idempotent()` routes need an `Idempotency-Key` header (16–128 characters). The same key and request replay the first result with `Idempotent-Replay: true`. The same key with a different request returns 409 (`IDEMPOTENCY_KEY_REUSED`). A request still running returns 409 (`IDEMPOTENCY_IN_PROGRESS`). A failed request frees the key.

**UI (`packages/ui`)**: `EmptyState` and `ErrorState` (Pen HP/State/EmptyState and HP/State/ErrorState).

**Tokens added**: `--hp-space-14` (14 px filter padding) and `--hp-audit-detail-width` (400 px), both exact Pen values.

## Tests

- **API (13 new, real database):**
  - The trigger refuses UPDATE, DELETE and TRUNCATE for the application's user.
  - Granting a permission is audited with before, after, MFA time and request ID. A retry returns the same result and a reused key returns 409.
  - A missing Idempotency-Key returns 400.
  - The 15-minute MFA recency is enforced.
  - At least two STAFF_ADMINs are kept.
  - Removing a permission is audited.
  - Access to staff administration by actor: 404 for signed-out people and customers, 200 for STAFF_ADMIN.
  - MFA reset: yours is refused; another admin's is reset, their sessions end and it's audited.
  - Viewer: cursor paging covers 30 entries with no overlap, search works, and more than 100 per page returns 400.
  - Viewer access: 404 for customers, 403 without AUDIT_VIEW.
  - Another person's session returns 404, and your own is ended.
  - **The limiter counts across two API instances**: the sixth sign-in attempt through either instance gets 429, and the fifth failure is audited once.
- **Browser (1 new, 375 and 1440 px):** the audit viewer loads, passes axe with no horizontal scroll, and shows the empty state for unmatched filters.
- **Totals:** 58 API tests and 73 browser tests pass.

## Screens checked

`/admin/audit` compared with Pen frame 101 (nmsXn and l4tuGM) at 1440 px, plus the 375 px layout. Differences:

1. Paging uses "‹ Newest" and "Next ›" instead of numbered pages. TECH-02 §3 requires cursor paging for audit lists, and cursor paging has no page numbers. The header count reads "Showing N entries", not "124 results", because a total count is not computed.
2. The "Export" button is left out; exports are T13-03.
3. The Pen filters are "Status / Assigned / Date"; the audit log uses "Action / Date", because audit entries have no status or assignee.
4. Entry references are shown as `AL-` plus the last 6 hex characters of the UUID (Pen: `AL-88213`), because entries have no separate reference number.
5. The request ID shows in full rather than shortened, so support can copy it.
6. The embedded "History" panel (HP/Admin/AuditEntry) waits for the first record page that shows history (catalogue, T02-01). `listAudit` already filters by record type and ID for it.

## Questions / conflicts found

- **Design against TECH, paging:** see difference 1. TECH-02 §3 is followed.
- **Old rate-limit rows:** expired `rate_limit_buckets` and `idempotency_keys` rows should be removed by `cleanup.daily`. `RateLimiter.removeExpired()` exists; the job arrives with the first clean-up work (T01-05).
- **PUBLIC_READ and SEARCH:** these classes exist, but no public route uses them yet. Catalogue and search tickets add `@RateLimit` to their routes.
