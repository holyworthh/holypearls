## Plan as built
1. One **proof per order item**, created with the order (checkout or accepted quote). Whether it's needed comes from the product rule (OPS-FR-018): NOT_REQUIRED, or PREPARING.
2. **Staff** (PROOF_MANAGE) prepare a DRAFT version: views (each a PROOF file) and the customer-facing production details.
3. **Publishing** freezes the version (service and database trigger), supersedes an earlier waiting version, sets the proof AWAITING_APPROVAL and emails the customer.
4. **The customer** views the proof, then approves (tick plus email code), requests changes, or asks a question.
5. **Approval does not move the item:** release rules are T07-01's, so the item stays AWAITING_PREREQUISITE ("Done when").

## What was built

### Data (migration `0031_proofs`)
- **New tables:**
  - `proofs` (one per order item, its status and requirement);
  - `proof_versions` (number, status, views as file references, details, who published it and when);
  - `proof_comments` (questions, change requests, staff replies, on their version);
  - `proof_decisions` (insert-only, one per version).
- **A trigger refuses any change to a published version** except its status, and refuses deleting it.
- **Backfill:** proofs are created for existing order items (PREPARING).
- **File access:** a published version's files can be opened by whoever can open the order, and by PROOF_MANAGE staff. Drafts stay staff-only.

### Customer: `/orders/[id]/proofs/[proofId]` (Pen 26, 49, 50)
- **The bar:** order, title, status chip, a version switcher, and "Item N of M".
  - Before approval the title is **"Production proof preview"** (FUL-FR-002).
  - After approval it reads **"APPROVED FOR PRODUCTION"**, with the lock note.
- **The dark viewer:**
  - zoom with the buttons, keyboard (+/−) and pinch;
  - fit to screen;
  - a view switcher (Front, Back, details);
  - the preview loads first, and the page rendition loads when zoomed in (TECH-04 §10).
- **The panel's tabs:**
  - **Comments**, numbered, with staff replies;
  - **Details** (placement, dimensions, colour reference, quantity, production notes);
  - **History** (sent, changes requested and approved, with who and when).
- **Decisions:**
  - **Approve for production** needs the tick ("I have reviewed the artwork, spelling, placement and specifications shown.") and an email code within 24 hours. The code dialog continues the approval. Pressing twice is safe.
  - **Request changes** takes a note: the version and proof become CHANGES_REQUESTED.
  - **Ask a question** stays undecided.
- **The order page** lists each item's proof: "Review proof V1", "Approved proof V2" or "Proof being prepared".
- **Access:** the same as the order; anyone else gets 404.

### Staff: `/proofs` and `/proofs/[id]` (Pen 112)
- **Proofs to prepare,** oldest first, and an Approved tab.
- **Artwork review:** files NEEDS_REVIEW or PROCESSING. **Mark READY**, or **Reject file** with a required note. Audited.
- **Proof preparation:**
  - start V1, or a new version (copying the latest);
  - views with uploads (SVG, PDF, AI or PNG);
  - production details, and the customer's own files;
  - Save draft;
  - **Publish VN**, after confirmation, refused until every file is READY;
  - versions with statuses and notes;
  - comments on the latest version, and a reply box.
- **Emails:** `proof_ready` ("Your proof is ready", with the order's secure link).

## Questions and conflicts
1. **Item status after approval:** approving doesn't queue the item. TECH-01 §4 moves AWAITING_PREREQUISITE → QUEUED when all prerequisites are met, which is T07-01's release logic. This matches "item stays waiting until approval".
2. **The proof email** links to the order (purpose ORDER), and the order page lists the proof. Guest links target one record; the proof belongs to the order.
3. **Proofs for orders made before this ticket** were created as PREPARING and REQUIRED. Only dev and staging have such orders.
4. **Quote orders:** lines that aren't a catalogue configuration (described items) always need a proof.
